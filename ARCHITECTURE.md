# EngramVault Architecture

**English** · [🇮🇹 Italiano](ARCHITECTURE.it.md)

---

This document outlines the architectural decisions, data model, and internal workings of **EngramVault**.

## 1. Core Principles

1. **Immutable Source of Truth:**
   Original AI conversations are never altered or replaced by lossy summaries. They remain stored intact in the database as auditable primary sources.
2. **Derived Knowledge Layer:**
   Distilled knowledge (facts, claims, decisions) lives as a *derived* layer on top of the raw archive. Every piece of knowledge preserves provenance pointers (`source_message_id`, `source_conversation_id`) back to the originating dialogue.
3. **Epistemic Cleanliness (Separation of Facts vs Claims):**
   - `FACT`: Statements made or confirmed by the user (e.g. owned equipment, preferences, homelab topology parameters).
   - `CLAIM`: Technical advice, analysis, or opinions generated by AI models (e.g. "Type II tapes are best suited for rock music").
4. **Temporal Dimension (SCD Type 2):**
   User state evolves over time (purchases, sales, updated decisions). Facts maintain temporal validity tracking via `valid_from`, `valid_until`, `is_current`, and `supersedes_id`.
5. **Zero-Overhead on Homelab (CPU-Only):**
   No heavyweight, memory-hungry external vector database daemon. The entire system operates out of a single SQLite database file (`vault.db`), with FTS5 lexical search and embeddings stored as compact BLOBs.

## 2. Data Model (Relational Schema)

```
[ conversations ] 1 ──< [ messages ] 1 ──< [ chunks ] (FTS5 indexed)
       │                      │
       │                      │ (source_message_id)
       │                      ▼
       └──────────────> [ statements ] (FACT vs CLAIM)
                              │
                              ▼
                         [ entities ]
                              │
                              ▼
                         [ relations ]
```

### Table Schema

- `conversations`: Conversation metadata (`id`, `provider`, `title`, `created_at`, `content_hash`).
- `messages`: Individual chat turns (`id`, `role`, `content`, `ts`, `sequence_order`).
- `chunks`: Segmented text chunks for semantic and lexical indexing.
- `chunks_fts`: SQLite FTS5 virtual table synchronized via automatic `AFTER INSERT`, `AFTER DELETE`, and `AFTER UPDATE` triggers.
- `entities`: Canonical names and categories of identified items (`name`, `category`, `normalized_name`).
- `statements`: Extracted triples/predicates (`subject`, `predicate`, `object`, `statement_type`, `author`, `is_current`, `valid_from`, `valid_until`).
- `decisions`: Architectural and technical decision records (`topic`, `decision_text`, `status`, `decided_at`).
- `relations`: Typed directed edges between entities in the knowledge graph.

## 3. Hybrid Retrieval Engine (RRF)

Purely semantic vector search frequently fails on exact product models, serial numbers, and alphanumeric codes (e.g. `TDK SA-X`, `Maxell XLII-S`, `Audient iD22`), confusing them with generic categories.
Conversely, lexical BM25 search misses conceptual synonyms and semantic paraphrases.

**EngramVault** bridges both worlds using **Reciprocal Rank Fusion (RRF)**:

$$RRF(d) = \frac{w_{bm25}}{k + rank_{bm25}(d)} + \frac{w_{vec}}{k + rank_{vec}(d)}$$

- $rank_{bm25}$: Document rank within SQLite FTS5 BM25 results.
- $rank_{vec}$: Document rank according to cosine similarity of the embedding vector.
- Smoothing constant $k = 60$.

## 4. Integration with Local and External AI

The `engramvault.llm.client` module interfaces with OpenAI-compatible endpoints (including local Ollama instances or cloud gateways for Gemini, Claude, OpenAI, Groq, DeepSeek):

1. **Synthetic Query Processing:** Sends only the most relevant locally-retrieved chunks and verified facts to the model, conserving tokens and preserving privacy.
2. **Structured Extraction:** The `extract_knowledge_with_llm()` utility powers batch extraction of entities and complex relationships.
